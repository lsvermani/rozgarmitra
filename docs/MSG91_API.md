# MSG91 server-side OTP API

WhatsApp/SMS OTP delivered through MSG91's **server-side** APIs — preferred over
the [OTP Widget](MSG91_OTP.md) because the authkey never reaches a client.

---

## Why this over the widget

| | Widget | Server-side API (this) |
|---|---|---|
| Authkey in browser/APK | **Yes** | **No** |
| OTP generated by | MSG91 | This app (CSPRNG) |
| OTP stored hashed | No (widget verifies) | **Yes** |
| Attempt limit / cooldown | MSG91's | **This app's** |
| OTP appears in a URL | Yes (verify is `GET ?code=`) | **No** |

MSG91 is used **only to deliver**. The code is generated with
`crypto.randomInt`, stored as an HMAC-SHA256 digest, and verified locally — so
MSG91's `GET Verify OTP` endpoint is never called and the code never enters a URL
or an access log.

---

## Setup

```env
OTP_PROVIDER=msg91api
MSG91_API_ENABLED=true
MSG91_API_AUTHKEY=<from MSG91 panel>
MSG91_API_TEMPLATE_ID=<OTP template UUID - must contain {code}>
MSG91_API_SENDER=MSG91
```

The template must contain a `{code}` placeholder, otherwise MSG91 rejects the
send. `POST /admin/whatsapp/test-connection` validates the authkey without
sending a message.

---

## Endpoint used

```http
POST https://control.msg91.com/api/v5/otp/{templateId}
authkey: <key>
Content-Type: application/json

{ "mobile": "918699142699", "OTP": "483921", "sender": "MSG91" }
```

Only delivery happens here — see the same route under `/api/auth/whatsapp/send-otp`.

## Failure handling

MSG91 uses two response shapes and both are handled explicitly, so a `200`
carrying an error is never treated as success:

```jsonc
{ "type": "success" }
{ "type": "error", "message": "...", "code": "201" }
{ "status": "fail", "hasError": true, "errors": "Unauthorized", "code": "401" }
```

Anything unrecognised fails closed.

| Code | Shown to user as |
|---|---|
| `201` / `1136` / `401` | "OTP service is not available right now." |
| `1512` / `1513` | "OTP service is temporarily unavailable." |
| `1523` | "This number cannot receive the code." |

Raw provider messages are never returned to a user.

## Testing

```bash
MSG91_API_ENABLED=true MSG91_API_AUTHKEY=<probe> node scripts/msg91-api-test.js
```

30 checks: provider registration, the authkey never appearing in any projection,
disabled/unconfigured failing closed, a bad key failing without throwing or
leaking, and every error code mapping to a safe sentence.

A real send is **not** exercised — that would cost money and message a real
number. The suite proves the failure paths, which are the ones that must never
regress.
