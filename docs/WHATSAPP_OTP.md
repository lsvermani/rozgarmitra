# OTP delivery provider

The active transport, taken from `OTP_PROVIDER` in `backend/.env`:

| Provider | Transport | Cost |
|---|---|---|
| `otpdev` | OTP.dev — SMS, WhatsApp, Telegram, Viber, voice, email | **Paid, per delivered message** |
| `whatsapp` | Meta WhatsApp Business Cloud API | Paid, per conversation |
| `demo` | Nothing is sent; the code is only in the response | Free (development) |

# WhatsApp OTP Integration (Meta Cloud API)

OTPs delivered through the **official Meta WhatsApp Business Cloud API**.

```
Android app / Web ──HTTPS──► Backend API ──HTTPS──► WhatsApp Cloud API
                                  │
                             MongoDB
                       (users, whatsappotps)
```

**Credentials live only on the backend.** Neither the Android app nor the browser
ever holds the Meta access token, phone number ID, or the OTP hashing pepper.

---

## 1. What you must obtain from Meta

These values cannot be generated by this application. Get them from
**Meta Business Manager → WhatsApp Manager**, with the business number
**+91 8699142699** onboarded:

| Variable | Source | Notes |
|---|---|---|
| `WHATSAPP_ACCESS_TOKEN` | **Meta** | Use a **permanent System User token**, not the 24-hour temporary one |
| `WHATSAPP_PHONE_NUMBER_ID` | **Meta** | From *API Setup*. This is **not** the phone number |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | **Meta** | The WABA (WhatsApp Business Account) id |
| `WHATSAPP_OTP_TEMPLATE_NAME` | **Meta** | Name of an **approved AUTHENTICATION** template |
| `WHATSAPP_OTP_LANGUAGE_CODE` | You | Must match the template's language, e.g. `en` |

This one you generate yourself:

| Variable | Source | Notes |
|---|---|---|
| `WHATSAPP_OTP_PEPPER` | **Generated** | `openssl rand -hex 32`. Rotating it invalidates in-flight codes |

Set them in `backend/.env` (gitignored). Never paste them into Dart, JSX, or Git.

### Important: the App ID and App Secret are NOT what you need

A Meta **App ID** (the number in the `/apps/<id>/dashboard/` URL) is used for OAuth
and Embedded Signup. A Meta **App Secret** is used to prove ownership of that App ID
in an app-secret-proof exchange. **Neither has any role in this integration.**

Meta issues four separate identifiers, and confusing them is the single most common
setup error:

| Identifier | Example shape | Where it lives | Needed here? |
|---|---|---|---|
| **Meta App ID** | `2300…` | Dashboard URL / App settings | ❌ no |
| **App Secret** | `32 hex chars` | App settings → Basic | ❌ **never** — see below |
| **Business Portfolio ID** | `9xxxxxxx` | Business Settings → portfolios | ❌ no |
| **WABA ID** | `1xxxxxxxxxxxxx` | API Setup panel | ✅ |
| **Phone Number ID** | `1xxxxxxxxxxxxx` | API Setup panel | ✅ |
| **Access Token** | `EAAG…` | API Setup / System User | ✅ |

> **⚠️ Never put an App Secret in `.env`, in source, or in a chat.**
> The WhatsApp Cloud API authenticates with an **Access Token** only. If a secret
> has been shared anywhere it should be treated as compromised and **rotated
> immediately** in *App settings → Basic → Show → Reset*.

Only the last three go into `.env`. The App ID is not used by this integration.

### Two kinds of access token

Meta's setup gives you a **temporary** token first (Step 3 of their guide, the
*Generate access token* button). It is fine for a smoke test but **expires in 24
hours**, so it is not what production should use.

For a permanent token, create a **System User** and generate a token with these
three permissions:

- `business_management`
- `whatsapp_business_messaging`
- `whatsapp_business_management`

Missing `whatsapp_business_messaging` is the usual cause of a token that
authenticates fine but cannot send.

### Verifying credentials without revealing them

Run this yourself in a terminal. It prints only your sender number's masked
identity — the token stays in your shell and is never sent to me:

```bash
curl -s "https://graph.facebook.com/v23.0/<PHONE_NUMBER_ID>?fields=display_phone_number,verified_name" -H "Authorization: Bearer <TOKEN>"
```

If that returns your number, the credentials are good. Then put them in
`backend/.env` and use **Admin → WhatsApp OTP → Test WhatsApp Connection**.

### Does the existing configuration support this number?

Not yet — and that is expected. **WhatsApp Business Account onboarding is a Meta-side
process that cannot be done from code.** Meta requires you to:

1. Create/choose a Meta Business Portfolio and Business Manager.
2. Add a WhatsApp Business Account (WABA).
3. Register **+91 8699142699** and complete OTP verification *in Meta's UI*.
4. Create and submit the authentication template (§2) for approval.

Only after Meta issues the Phone Number ID and a token can this code send anything.
The integration is complete and testable without that step (`WHATSAPP_TEST_MODE=true`).

## 2. Template setup (manual, in Meta)

OTP delivery uses a **template message**, because Meta only permits authentication
templates to carry a one-time code.

| Field | Value |
|---|---|
| Template name | e.g. `otp_verification` (must match `WHATSAPP_OTP_TEMPLATE_NAME`) |
| Category | **AUTHENTICATION** |
| Language | e.g. `English (en)` |
| Body | `{{1}}` is your code. Suggested copy:<br>`Your verification code is {{1}}.`<br>`This code expires in 5 minutes.`<br>`Do not share this code with anyone.` |

Submit it for review — Meta must approve it before messages will send.

```env
OTP_LENGTH=6
OTP_EXPIRY_MINUTES=5
OTP_MAX_ATTEMPTS=5
OTP_RESEND_SECONDS=60
OTP_PER_PHONE_HOURLY_LIMIT=5

WHATSAPP_RATE_MAX_REQUESTS=30

```

`WHATSAPP_ENABLED=false` is the default. The endpoints then report the service
unavailable and the app keeps using the **existing SMS / Firebase login** — nothing
breaks. That is why this is safe to merge before Meta onboarding finishes.

## 4. API endpoints

Public — rate limited to 30 requests / 15 min per IP:

| Method | Path | Body |
|---|---|---|
| GET | `/api/auth/whatsapp/status` | — |
| POST | `/api/auth/whatsapp/send-otp` | `{ phone, role?, purpose? }` |
| POST | `/api/auth/whatsapp/resend-otp` | `{ phone, role?, purpose? }` |
| POST | `/api/auth/whatsapp/verify-otp` | `{ phone, otp, role?, name?, purpose? }` |

```jsonc
// POST send-otp -> 200
{ "success": true, "message": "OTP sent successfully. Please check your WhatsApp.",
  "expiresIn": 300, "resendAfter": 60 }

// POST verify-otp -> 200  (same envelope as the existing SMS login)
{ "success": true, "verified": true, "token": "<app JWT>", "user": { } }
```

Admin — requires a signed-in administrator:

| Method | Path | Permission |
|---|---|---|
| GET | `/api/auth/whatsapp/admin/config` | `settings.configure` |
| POST | `/api/auth/whatsapp/admin/test-connection` | `settings.configure` |
| GET | `/api/auth/whatsapp/admin/stats?from=&to=` | `logs.view` |
| GET | `/api/auth/whatsapp/admin/failures` | `logs.view` |

A worker or job creator gets **403**; an anonymous caller gets **401**.

## 5. Data model

New collection **`whatsappotps`**. One live row per `(phone, purpose)` — a new code
replaces the previous one, so a stale code can never remain usable.

```js
{
  phone: '+918699142699',   // E.164
  national: '8699142699',   // matches User.mobile
  otpHash: '<HMAC-SHA256>', // NEVER the plaintext code
  purpose: 'registration',
  attempts: 0,
  verified: false,
  expiresAt: ISODate,       // TTL index — MongoDB removes the row automatically
  lastSentAt: ISODate,      // resend cooldown + per-hour limit
  deliveryStatus: 'sent',   // pending | sent | failed
  deliveryErrorCode: ''     // Meta code only, never the response body
}
```

`User` gains `phoneVerified`, `phoneVerifiedAt`, `phoneVerifiedVia`. Existing
documents default to `false` — nothing is retroactively marked verified.

## 6. Security

| Requirement | How it is met |
|---|---|
| Secure generation | `crypto.randomInt` (CSPRNG). **Never** `Math.random()` |
| Hashed storage | HMAC-SHA256 + server-side pepper; plain codes never persisted |
| No OTP in responses | Never returned by `send-otp`; only under test mode outside production |
| No OTP in logs | Neither the code nor Meta response bodies are logged |
| No token exposure | Read from env in one module; never sent to a client |
| Expiry | 5 minutes, in code **and** via a MongoDB TTL index |
| Attempt limit | 5, counted server-side |
| Resend cooldown | 60 seconds, from `lastSentAt` |
| Rate limiting | Per-IP limiter + per-number hourly limit (DB-backed, survives restart) |
| Timing attacks | `crypto.timingSafeEqual` for the hash comparison |
| Replay | The digest is **cleared** the instant a code is used |
| RBAC | `requirePermission` on every admin route |
| Validation | `express-validator`; the phone is re-normalised server-side, never trusted from the client |

`express-mongo-sanitize` is already applied globally in `app.js`. Meta is reached
over HTTPS only — the Graph host is not overridable by configuration.

## 7. Clients

**Web (admin)** — `admin/src/pages/WhatsAppSettings.jsx`, routed at `/admin/whatsapp`.
Credentials appear as booleans plus a **masked hint** (last 4 chars). There is
deliberately no input that could write a secret to the browser.

**Android / Flutter** — `mobile/lib/screens/auth/whatsapp_otp_screen.dart`, routed
at `/whatsapp-login?role=…`. Phone entry → 6-digit code → countdown → resend → verify.
The countdown is **presentation only**; the server enforces the real limits.

The existing `/login` (SMS/Firebase) flow is untouched, so enabling this changes
nothing for anyone who does not open the WhatsApp route.

## 8. Development and testing

```bash
# Terminal 1 - run the backend with the safe test mode
cd backend
WHATSAPP_ENABLED=true WHATSAPP_TEST_MODE=true npm start

# Terminal 2 - run the suite (no real messages, no Meta account needed)
node scripts/whatsapp-otp-test.js
```

Test mode returns the code as `testOtp` so a client can complete a verification.
It is **refused automatically when `NODE_ENV=production`**, so it cannot leak a
real code to a real user even if left set by accident.

## 9. Production deployment

1. Complete Meta onboarding (§1) and get the template approved (§2).
2. Put the five `[FROM META]` values and the pepper in the server's secret store.
3. Set `WHATSAPP_TEST_MODE=false` and `NODE_ENV=production`.
4. Serve the API over **HTTPS** (cleartext is blocked in release builds).
5. Admin panel → **WhatsApp OTP** → *Test WhatsApp Connection*.
6. Send one real OTP to your own number and confirm it arrives.

## 10. Troubleshooting

| Symptom | Cause |
|---|---|
| `WhatsApp OTP is not configured...` | `WHATSAPP_ACCESS_TOKEN` / `WHATSAPP_PHONE_NUMBER_ID` unset |
| No failures recorded but no message arrives | Template not approved, or recipient outside the window |
| Meta `131047` | Delivery failed — recipient may not have WhatsApp |
| Meta `131009` | Number is not a valid WhatsApp recipient |
| Meta `131026` | Recipient must be added to the allow-list during onboarding |
| Meta `131056` | Message limit reached — too many sends to this number |
| `template does not exist` | Template name in `.env` does not match Meta exactly |
| Codes stop verifying after a deploy | `WHATSAPP_OTP_PEPPER` changed |
| 429 on every request | Resend cooldown or per-hour limit reached — wait |

**Admin → WhatsApp OTP → Recent delivery failures** shows the Meta error code for
any failed attempt. Numbers are masked; OTP contents are never stored.

## 12. Which values come from where

**From Meta** (you must supply): `WHATSAPP_ACCESS_TOKEN`,
`WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`,
`WHATSAPP_OTP_TEMPLATE_NAME`.

**Generated by you:** `WHATSAPP_OTP_PEPPER`.

**Chosen by you:** `WHATSAPP_API_VERSION`, `WHATSAPP_OTP_LANGUAGE_CODE`, all OTP
policy and rate-limit values, and `WHATSAPP_ENABLED` / `WHATSAPP_TEST_MODE`.

Nothing in this list has been invented or hard-coded. The application ships with
`WHATSAPP_ENABLED=false` and empty credentials.
