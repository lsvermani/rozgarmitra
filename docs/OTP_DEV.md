# OTP.dev integration

Transport for the WhatsApp OTP flow when `OTP_PROVIDER=otpdev`.

---

## ⚠️ OTP.dev is not free

Its published per-message pricing (USD, "no monthly fees, pay only for successful
messages"):

| Channel | From |
|---|---|
| SMS | **$0.007** |
| WhatsApp | **$0.015** |
| Viber | $0.01 |
| Voice OTP | $0.01 |
| Email | $0.005 |
| Telegram | $0.03 |

Note that **OTP.dev's WhatsApp channel costs roughly twice its own SMS channel**, so
routing through it is not a cheaper way to get WhatsApp OTPs. Prices vary by country;
India is priced separately on their pricing page. "Start for free" means a free
trial/signup, not a free service.

**`demo` is the only genuinely free provider**, and it is the default.

## Setup

1. Create an account and get an API key from your OTP.dev dashboard.
2. Create a **template** in their dashboard. The template body **must contain a
   `{code}` placeholder** — a template without one fails every send with error
   `1624`.
3. Add to `backend/.env`:

```env
OTP_PROVIDER=otpdev
OTPDEV_API_KEY=<your key>
OTPDEV_TEMPLATE_ID=<template uuid>
OTPDEV_CHANNEL=sms        # sms | whatsapp | telegram | viber | voice | email
OTPDEV_SENDER=OTP.dev
```

4. Restart the backend and use **Admin → WhatsApp OTP → Test WhatsApp Connection**.

## What the code does

`backend/src/services/otpdevService.js` sends:

```http
POST https://api.otp.dev/v1/verifications
X-OTP-Key: <key>
Content-Type: application/json

{ "data": { "channel": "sms", "sender": "OTP.dev",
            "phone": "918699142699", "template": "<uuid>", "code": "483921" } }
```

The phone number is sent as **digits only, without `+`**, which is OTP.dev's
requirement — `normalisePhone()` produces E.164 and this service strips the `+`.

### The code is supplied, not generated by OTP.dev

OTP.dev accepts either `code_length` (they generate one) or `code` (we supply one).
**This integration always supplies `code`.** Three reasons:

1. **Their verify endpoint puts the code in a URL.**
   `GET /v1/verifications?code=1234` means the code lands in web-server logs, proxy
   logs and browser history. Verifying locally avoids that entirely.
2. **The application keeps control** of expiry, the 5-attempt limit and the
   60-second resend cooldown, rather than trusting a remote service to enforce them.
3. **The code never has to leave the server** to be checked, so our existing HMAC
   hashing and TTL-cleanup model applies unchanged.

Error `1629` rejects sending both `code` and `code_length`, so only `code` is sent.

## Error codes handled

| Code | Meaning | Shown to user as |
|---|---|---|
| `1136` | Not authorised (bad API key) | "Service not available" |
| `1512` / `1513` | Invalid / unknown template | "Service not available" |
| `1515` | Invalid channel | "Channel unavailable" |
| `1523` | Invalid recipient number | "This number cannot receive the code" |
| `1620`–`1624` | Missing sender / phone / template, bad length, no `{code}` | "Service not available" |
| `1629`–`1632` | Code/length misuse | "Service not available" |
| `1705` | Invalid payload | "Service not available" |

Raw provider messages are never surfaced to a user; only the codes above are
mapped to short sentences.

## Testing without spending credit

```bash
WHATSAPP_TEST_MODE=true npm start
node scripts/whatsapp-otp-test.js
```

Test mode bypasses delivery entirely and returns the code as `testOtp`. It is
**refused automatically when `NODE_ENV=production`**.

`testConnection()` is deliberately cheap: it sends a request with an intentionally
invalid recipient (`"1"`). OTP.dev validates the API key and template *first*, then
rejects the number with `1523` — so a `1523` proves the credentials are valid
**without delivering a message or being charged**.
